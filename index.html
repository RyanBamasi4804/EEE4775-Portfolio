Application 3 Overview

Application 3 demonstrates an interrupt-driven real-time system using an ESP32-S3 and FreeRTOS. A button press is treated as an asynchronous spacecraft ground command. The GPIO interrupt service routine responds to the event and signals FreeRTOS tasks to perform the bottom-half work.

The application demonstrates two methods of communicating from an ISR to a task: a binary semaphore and a direct task notification. The application also includes periodic background workloads that can be used to study the effect of processor contention on response latency.

ISR Operation

  1. Read the current time using esp_timer_get_time().
  2. Reject button edges occurring inside the debounce interval.
  3. Set the ISR timing GPIO HIGH.
  4. Record the ISR entry timestamp.
  5. Increment the observed press counter.
  6. Give the binary semaphore.
  7. Send the direct task notification.
  8. Set the ISR timing GPIO LOW before returning.
  9. Optionally request a context switch when a higher-priority task was awakened.

Interpretation

The measured results showed a significantly lower response latency for the direct task-notification path than for the binary semaphore path. This demonstrates that the synchronization mechanism used between an ISR and a task can affect real-time response performance.

Induced Failure

Removing the ISR Context Switch

The application can be used to demonstrate the effect of removing the ISR-triggered context switch. The relevant statement is: 

portYIELD_FROM_ISR(higher_woken);

When this operation is disabled, the ISR can still signal the waiting task, but the higher-priority task is not immediately scheduled as part of the ISR exit. This can increase the response latency of the bottom-half task.

Failure Result

The induced failure demonstrated that the system could continue to function while its real-time response became worse. This is important because a real-time system can produce the correct functional result while still violating its timing requirements.

Measured failure result: 1187 µs

With the ISR context-switch request disabled, the measured notification latency increased to 1187 µs compared with 30 µs during normal operation. This represents approximately a 39.6× increase in response latency.

Engineering Reflection

What Would I Do Differently?

If I were to do this project again, I would spend more time planning and testing each part of the system before putting everything together. I found that small changes to task priorities, timing, and the way tasks communicate can have a noticeable effect on the system's behavior. I would also collect more measurements during testing so I could compare the different configurations more reliably instead of relying on only a few observations.

What Was Harder Than Expected?

The hardest part was understanding how the different parts of the real-time system interacted with each other. The ISR itself was relatively straightforward, but understanding how the ISR communicates with the FreeRTOS tasks and how task priorities and CPU load affect response time was more difficult. It was especially interesting to see that the system could still function while its timing performance became worse under certain conditions.

What Was the Most Valuable Thing I Learned?

The most valuable thing I learned was that in a real-time system, getting the correct result is only part of the problem. When the result occurs can be just as important. This project helped me understand why interrupts should be kept short, why work is often moved into tasks, and how task priorities and synchronization methods affect system responsiveness. I think this is something I will carry into future embedded systems projects because it changes how I think about both designing and testing software.
